# アバター描画方式の比較

## 目的

StudyUsの2Dアバター描画方式を後から比較・変更できるように、候補の特徴と
選定基準を記録する。現時点ではCanvas図形描画のみ実装済みであり、
その他の方式は未導入・未決定である。

顔検出は描画方式から分離し、すべての方式が共通の`AvatarPose`を受け取る。

```text
カメラ → MediaPipe → AvatarPose → 選択したRenderer → 画面
```

## 共通入力

描画方式を変更しても、次の入力形式は維持する。

```ts
type AvatarPose = {
  faceX: number
  faceY: number
  rotation: number
  eyeOpenLeft: number
  eyeOpenRight: number
  mouthOpen: number
}
```

カメラ映像そのものはRendererへ渡さない。顔検出済みの数値だけを渡すことで、
描画方式とMediaPipeを独立して変更できるようにする。

## 比較

| 方式 | 実装工数 | 素材制作 | 表情追従 | 複数表示 | 外部依存 | 現在の状態 |
| --- | --- | --- | --- | --- | --- | --- |
| Canvas図形 | 小 | 不要 | 容易 | 良い | なし | 実装済み |
| PNG/SVGパーツ | 小〜中 | 必要 | 容易 | 良い | なし | 未実装 |
| PixiJS | 中 | 必要 | 容易 | とても良い | あり | 検討中 |
| Rive | 中 | `.riv`制作が必要 | 良い | 良い | あり | 検討中 |
| Live2D Cubism | 大 | イラスト分割とモデリングが必要 | とても良い | 要検証 | あり | 検討中 |

## Canvas図形描画

### 概要

Canvas 2D APIで円、曲線、塗りなどを組み合わせて描画する。現在の
`frontend/src/features/avatar/renderer.ts`がこの方式である。

### 長所

- 外部ライブラリと画像素材が不要
- 実装とデバッグが簡単
- 色や形をコードから変更しやすい
- `AvatarPose`との接続を確認しやすい

### 短所

- 複雑なキャラクターデザインをコードだけで表現しにくい
- デザイナーが見た目を編集するにはコード変更が必要
- 髪や服の自然な揺れを作り込むと実装量が増える

### 適する用途

- 顔検出と通信の技術検証
- シンプルなマスコット
- 素材が完成するまでの代替表示

## PNG/SVGパーツ描画

### 概要

体、顔、髪、目、口、アクセサリーを別画像として用意し、CanvasまたはDOM上で
重ねて描画する。まばたきや口の開閉は画像差し替え、顔の移動・傾きは座標変換で
表現する。

### 長所

- 現在のCanvas構成を大きく変えずに見た目を改善できる
- デザイナーと開発者の担当範囲を分けやすい
- Live2Dほどのモデリング作業を必要としない
- 髪、服、色、アクセサリーの組み合わせを作りやすい

### 短所

- パーツ画像の命名、基準位置、描画順を統一する必要がある
- PNGは拡大時に画質が落ちる可能性がある
- 表情パターンを増やすほど素材数が増える

### 適する用途

- ちびキャラ、動物、ピクセルアート
- 短納期で見た目とカスタマイズ性を両立したい場合

## PixiJS

### 概要

WebGLを中心とした2D描画エンジンで、画像パーツをSpriteとして扱う。
サブウィンドウに複数ユーザーのアバターを同時表示する用途を想定する。

### 長所

- 多数のSpriteを効率よく描画できる
- パーツの座標、回転、拡大縮小、透明度を扱いやすい
- フィルターやマスクなどの表現を追加できる

### 短所

- Canvasだけの場合より依存関係と学習項目が増える
- 描画エンジンであり、キャラクター素材は別途必要
- WebGLコンテキストやリソース解放を管理する必要がある

### 採用判断

PNG/SVG方式で複数人表示時の性能が不足した場合、またはSprite管理が複雑になった
場合に検討する。最初から導入する必須性はない。

## Rive

### 概要

Rive Editorで作成した`.riv`ファイルをWebランタイムで描画する。
アニメーションとState Machineを素材側に保持できる。

### 長所

- ベクター形式で拡大しても表示が荒れにくい
- アニメーション担当者がコード外で動きを編集できる
- 状態遷移や入力値によるアニメーションを設計できる
- TypeScript対応のWebランタイムがある

### 短所

- Rive Editorによる素材制作が必要
- WebランタイムとWASMが追加される
- MediaPipeの値とRive側の入力名を対応付ける設計が必要
- ランタイム更新時に`.riv`素材との互換性確認が必要

### 採用判断

ベクター表現と編集ツールによるアニメーション制作を重視し、制作担当者が
Riveを扱える場合に検討する。

## Live2D Cubism

### 概要

パーツ分けしたイラストをCubism Editorでモデリングし、Cubism SDK for Webで
描画する。VTuberに近い頭部回転、変形、髪や服の物理表現が可能である。

### 長所

- 顔追従の表現力が最も高い
- イラストの特徴を保ったまま立体感を表現できる
- 目、口、眉、頭部回転などのパラメーターが充実している

### 短所

- パーツ分けイラストと専門的なモデリングが必要
- SDK統合とパラメーター対応付けの工数が大きい
- 複数モデルを同時表示する場合は端末性能を検証する必要がある
- SDKとモデル双方のライセンス条件を確認する必要がある

### 採用判断

本格的なキャラクター表現を製品の中心に据え、素材制作とライセンス確認に
十分な時間を確保できる場合に検討する。

## 切り替え可能にする設計

各方式は共通インターフェースを実装する。

```ts
type AvatarRenderer = {
  render: (pose: AvatarPose) => void
  resize: () => void
  clear: () => void
  destroy: () => void
}
```

将来はRendererを直接コントローラーへ渡し、カメラと顔検出を停止せずに
描画方式だけを交換できる構造にする。

```ts
await controller.changeRenderer({ type: 'sprite', avatarId: 'student-01' })
```

RiveやLive2Dのように初期化コストが大きい方式は、選択されたときだけ
動的importする。未選択の描画ライブラリを初期バンドルへ含めない。

## アバター情報の共有

他ユーザーへカメラ映像を送信せず、Rendererに依存しない情報だけを送る。

```ts
type SharedAvatarState = {
  rendererType: 'canvas' | 'sprite' | 'pixi' | 'rive' | 'live2d'
  avatarId: string
  pose: AvatarPose
}
```

描画方式固有の素材URLや設定値は、信頼できるアバター定義から解決し、
他ユーザーから受け取った任意URLをそのまま読み込まない。

## 現時点の推奨順

1. Canvas図形で顔検出、停止処理、通信を確認する。
2. PNG/SVGパーツ方式を追加し、描画切り替えの設計を確定する。
3. 複数人表示で性能や管理上の問題が出た場合にPixiJSを検討する。
4. 制作体制と表現要件が固まった後にRiveまたはLive2Dを比較する。

短納期ではPNG/SVGパーツ方式を第一候補とし、RiveとLive2Dの導入は
素材制作時間とライセンス条件を確認してから決定する。

## 採用時に記録する事項

新しい方式を採用するときは、次を更新する。

- `docs/libraries.md`の採用状態、バージョン、ライセンス
- 素材ファイルの形式と配置場所
- Rendererへの入力とパラメーター対応表
- 初期化、切り替え、破棄の手順
- バンドルサイズと複数人表示時の性能測定結果
- 外部通信、ユーザーデータ、利用規約への影響
